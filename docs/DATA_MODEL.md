# V1 persistent data model

This is the planned server-owned player profile for V1. `schemaVersion` is `1`. It remains a specification until M2/M7 implement the profile loader and persistence boundary; no DataStore or profile-library integration exists yet. The profile is the minimum durable state needed to resume progression and resolve the Welcome first-Raid rule deterministically.

## Profile schema

| Field | Type and constraints | New-profile default |
| --- | --- | --- |
| `schemaVersion` | Integer; exactly `1` for this schema. | `1` |
| `scrap` | Non-negative bounded integer. Only the server changes it. | `50` |
| `creatures` | Array of at most four creature records; IDs unique within the profile. | One Mossling starter record. |
| `starterCreatureId` | Stable server-generated creature ID; must identify the protected starter record. | ID of the new Mossling. |
| `slotCapacity` | One of `2`, `3`, or `4`; must be at least the number of owned creatures. | `2` |
| `catalysts` | Non-negative integer counts keyed by `emberSeed`, `prismDust`, and `mossSpore`. | All `0`; the free tutorial choice is granted and consumed atomically and is not stored as inventory. |
| `standardCapsulePity` | `{belowUncommon: 0..3, belowRare: 0..8}`. Welcome purchases do not change it. | Both `0`. |
| `mutationRareMissCount` | Integer `0..8`; the only mutation pity counter. | `0` |
| `discoveredSpeciesIds` | Set of valid species IDs, max 12. | Contains `Mossling`. |
| `discoveredMutationFormIds` | Set of valid form IDs, max 24. A form is added when equipped. | Empty. |
| `tutorialCompleted` | Boolean; the one-time free tutorial mutation can complete once. | `false` |
| `welcomeCreatureId` | Stable creature ID awarded by the Welcome Capsule, or `nil` before it is claimed. Keep the ID after that creature is sold or transferred so the award cannot be claimed again. | `nil` |
| `hasCompletedFirstRaid` | Boolean. Once true, it never returns to false. | `false` |
| `firstRaidParticipation` | `nil` or `{raidId: string, completesAtUnix: integer}`. The server writes it as soon as participation begins and clears it when completion is finalized. | `nil` |

Each creature record is `{id: CreatureId, speciesId: SpeciesId, mutationFormId: FormId?}`. `id` is generated by the server and never reused; `speciesId` and optional `mutationFormId` must exist in the shared definition catalogs. A creature's active form is either absent or exactly one form. The starting creature is identified by `starterCreatureId`, not by species, so a later-acquired Mossling is ordinary.

There is no entitlement placeholder in the profile. The future cosmetic Game Pass is verified through Roblox's server-side ownership API; its result is not a source of gameplay currency, power, capacity, or ownership. See [MONETIZATION.md](MONETIZATION.md).

## Welcome first-Raid invariant

`welcomeCreatureId` identifies the only Welcome creature that can receive temporary protection. Protection is active when that ID is set and `hasCompletedFirstRaid` is false. The first-Raid participation marker is independent of whether the Welcome Capsule has already been claimed.

Any player already present in the server when RAID begins receives `firstRaidParticipation` immediately; character/base initialization does not delay the participation timestamp. A player joining during RAID receives it only when the original 15-second arrival-grace timestamp expires strictly before RAID-to-RESOLUTION. Store the current server Raid ID and the scheduled RESOLUTION-to-COOLDOWN Unix timestamp in `completesAtUnix`. Disconnect does not clear the marker or postpone the deadline. A profile load at or after the deadline finalizes completion before the profile is made available: set `hasCompletedFirstRaid = true`, clear the marker, and save the normalized profile. A load before the deadline keeps the same marker; it must not create a new participation entitlement. A late join whose grace lasts through RAID-to-RESOLUTION creates no marker for that Raid. PEACE and WARNING create none.

When the marker is finalized, protection ends even if the player was offline at the boundary. If the Welcome Capsule is claimed after `hasCompletedFirstRaid` becomes true, its creature receives no first-Raid protection. The permanent starter rule does not depend on this profile flag.

## Runtime-only state

Do not persist transient mechanics as ownership or progression:

- Shared phase timer, current server Raid phase, and arrival-grace start/expiry timestamps.
- Pending mutation reveal, pending client choice, or visual animation state.
- Theft target/base locks, channel and bank-hold timers, carried/dropped reservations, Tag cooldown/immunity, and per-Raid attempt counters.
- Online income scheduler and fractional payout remainder. No offline income is accrued.
- Connection/session metadata, remote rate buckets, UI selections, and cosmetic presentation cache.

Only the durable first-Raid participation marker crosses a disconnect because it records a real participation decision and a scheduled completion deadline. A theft transfer journal may be persisted as an operation record while reconciling a transfer, but it never makes an unbanked creature belong to the thief; committed ownership remains represented only in `creatures`.

## Defaults, validation, and migrations

- A missing profile creates the defaults above on the server. The starter ID is generated server-side and the initial Mossling is inserted exactly once.
- Validate type, bounds, catalog IDs, unique creature IDs, slot capacity, starter reference, pity ranges, Codex bounds, and marker fields before exposing the profile to services.
- `welcomeCreatureId` may refer to a creature no longer in `creatures`; ownership can later change, while the ID must remain to prevent another Welcome grant. `starterCreatureId` must always refer to the owned starter record.
- Version migrations are deterministic, sequential functions (`1 -> 2`, then `2 -> 3` as needed). Never skip a version or silently downgrade an unknown future schema. Version 1 has no prior persisted production format; a missing record uses the default factory, not a fabricated migration.
- Apply elapsed `firstRaidParticipation.completesAtUnix` before granting a loaded profile to gameplay. Normalization is idempotent.
- Malformed or corrupt records are quarantined or recovered from a verified backup. Do not replace unreadable data with defaults and then save over it. If recovery fails, keep the player out of persistence-dependent gameplay and surface an operational error.

## Ownership and save lifecycle

`PlayerDataService` is the only gameplay-facing owner of a loaded profile. A server-only `ProfileStore` adapter acquires a per-user session lock, loads, validates, migrates, and saves serialized data. Domain services request validated mutations through PlayerDataService; clients never submit a profile or authoritative field values.

Use bounded retry/backoff for transient load/save failures. Mark committed changes dirty, checkpoint during the session, save on player removal, and attempt bounded saves during shutdown. Do not acknowledge a durable transaction as saved until the store confirms it. On duplicate-session lock failure, do not allow two servers to mutate the same profile. Failed or interrupted transfer writes must reconcile from an idempotent journal to exactly one owner.

## Explicit exclusions

No Mythic pity or Mythic miss count, offline income, extra currencies, permanent pending mutation outcome, permanent target locks, Tag cooldowns, carried creature ownership, client-controlled save fields, or cosmetic entitlement placeholder is stored.
